## 2. 真增量清单（全部对齐 9 月路线，不是平行路线）

### 2.1 📷 截图通道（本次的核心交付）

`ui.md` §4 里一直挂着"截图识别（入口 B）未做"。本次补上：

| 件 | 说明 |
|---|---|
| `scripts/m1_screenshot_ohlcv.py` | 截图 → OHLCV，**纯颜色掩码 + 手工标定**（`10` §三的原设计，不用任何模型）。支持线性/对数价格轴。`--selftest` 合成图回环 60/60、≈1 像素 |
| `serve.py` 新增 `POST /api/shot` | 界面入口：上传截图 + 框选 + 4 个标定数 → **与库同一支归一化**（`vectors_from_matrix`，口径不漂移）→ 检索 → 界面正常渲染 |
| 界面「📷 查截图」面板 | 预览图上**点两下框选**蜡烛区 → 填首根时间/价格上下限/对数轴 → 查询。每次查询的原图、提取的 OHLCV、标定参数自动存档到 `results/shot_uploads/<时间戳>/` |
| `scripts/m1_shot_e2e_test.py` | 端到端回归（**改了 serve.py 或提取器就必跑**）：真库窗口 → 渲染 TV 风格截图 → 上传 → top-1 必须命中库内自身窗口 |

**关键设计决定——截图检索只比"形态 32 维"**：
把一段 K 线的形状压缩成 32 个数字叫"形态向量"；成交量那一路叫"量能通道"。
截图里读不出量能。如果拿"中性量能"混进 64 维检索，距离会多出一个**逐窗口不同**的项，
排序会被"谁的量能曲线本身比较平"带偏——这是**静默失真**。
所以截图查询只在形态 32 维上做（`serve.py` 的 `_search32`），界面上明写"量能通道不参与"。
**宁可少用一路信息，不许静默掺假。**

**验证**：端到端 3/3（线性轴、对数轴、contemp=0 的"跨币同时段排除"都过）；
浏览器实测：注入文件 → 框选标定（两点点击坐标换算正确）→ 查询 → 结果卡正常渲染
（#1 最像 LUNAUSDT 2021-03-29，距离 1.4 vs 标尺 10.7）。
文件选择框是浏览器原生行为没法自动化，其余全部实测。
