# 滚动补数据（增量并进检索库）· 结题页

> 2026-09-22 · 第一次实跑 · 脚本 `scripts/refresh.py`
> 上一版结账页：`results/live.md`（接实时拉取，2026-09-17）
> **一句话**：把库从"止于 2026-08-31"推进到"**止于 2026-09-21**"，
> 并把这件事做成**可重复、可校验、只动增量**的流程 —— 老数据经 4000 条抽样证明**一个字节都没动**。

---

## 1. 要解决什么（大白话）

检索库 2026-09-14 建成，数据止于 **08-31**。到 09-22 已经差 **21 天**，
而这个窟窿**每天自己长大一天**：下个月就是 51 天。

界面上「⚡ 看此刻」只能查"此刻"，**查不了这半个月里随便哪一刻**。

⚠️ 但要说清楚：**补数据不会让检索变得更准**（方向不可测的结论一个字没变）。
它解决的是**"有一段历史查不到"**。

## 2. 做了什么（六步，全部可断点续跑）

| 步 | 命令 | 结果 | 用时 |
|---|---|---|---|
| ① 存快照 | `--stage snapshot` | 4000 条老窗口指纹 + 流动性表快照（**改索引前**存，是唯一证据） | 秒级 |
| ② 下载 | `--stage fetch` | 每日归档 09-01~09-21 | 18s |
| ③ 合并 | `--stage merge` | 并进 `data/raw/1m`，原子替换 | 31s |
| ④ 重派生 | `--stage derive` | 131 个币重算 15m | 37s |
| ⑤ 流动性 | `--stage liquidity` | 重建 `pool_liquidity.parquet` | 6s |
| ⑥ 建索引 | `--stage index` | 只重算改动的币，其余复用分片 | 43s |
| ⑦ 体检 | `--stage verify` | 七项检查 | 秒级 |

**为什么走「每日归档」而不是月度归档**：缺口落在月中，月度 zip 要等下月初才生成（实测 09-22 时 2026-09 仍是 404），而**每日归档次日就有**。

## 4. ⭐ 核心证据：老数据一个字节都没动

**为什么这是关键**：增量的天然风险是 **"没重算"和"算错了"在结果上长得一模一样**。
所以"我用了增量"这句话本身没有说服力 —— 必须拿出**改动前的指纹**来比。

`--stage snapshot` 在改索引**之前**存下 4000 条随机老窗口的向量 SHA 指纹，`--stage verify` 改完再逐条比对：

| 检查 | 结果 |
|---|---|
| ① 行数一致（meta / shape / raw 三者） | ✅ 1,165,566 全对齐 |
| ② 币块连续不交错 | ✅ 122 块 / 122 币 |
| ③ 无重复窗口 + 每币时间严格递增 | ✅ 重复 0 条 |
| ④ ⭐ **老窗口逐字节没动**（4000 条抽样） | ✅ **指纹相同 shape 100.00% · raw 100.00%**；元数据最大偏差 **0.0000000000**；后续走势不一致 **0** 条 |
| ⑤ 每币窗口数只增不减 | ✅ 23/122 个币有变化，**变少的 0 个** |
| ⑥ 流动性表老日期逐位未变 | ✅ liq30 偏差 **0.0000000000**，缺失态变化 **0** 行 |
| ⑦ 时间上限推进 | ✅ 索引最晚 t1 = 2026-09-21 23:45 |

> **⑥ 是币池口径的守门人**：老日期的流动性指标若变了，等于"当时谁在前 20 名"被改写 → 币池口径漂移。
> 实测**零偏差** → 所以"没重算的那 30 个币复用旧分片"是正确的（它们的池判定确实没变）。

**回归测试**（索引变了必须重跑）：
- `verify_live_pipeline.py --n 40` → **40/40 结果逐条相同**，向量偏差 **0.00000000**，库内距离中位 5.74
- `smoke_all.py`（起服务→冒烟→关服务）→ **20/20 断言通过**，无白屏、无 NaN

## 5. ⚠️ 本轮踩的坑（最贵的资产，全部已修）

| # | 坑 | 危害 | 修法 |
|---|---|---|---|
| **1** | ⭐ **`norms_*.npy` 缓存没随索引长度失效** | **最危险的一个**：它是每个窗口的"向量长度"，增量重建后旧缓存短了 8,064 条 → 检索时切片越界（报错，算走运）；**若长度恰好合拍，会静默按错位取范数 → 距离全错、却不报错** | `retrieve.norms()` 把**长度当作缓存有效性的一部分**，对不上就重算覆盖；`build_index` 建完库**主动刷新**两份缓存 |
| **2** | `verify` ⑥ 的**检查方法本身**产生假警报 | 第一版写成"新表 liq30 是 NaN 就算失败"，把 **1,800 行"两边本来就都算不出"的格子**（新上市不足 30 天）判成"老日期被改写" → 零偏差却报 ❌ | 改量「**原本有值却变空**」；并把"两边都 NaN"的格子数单独打出来说明 |
| **3** | `merge` 无逐币容错 | 一个 0 字节文件会让**整轮 131 个币全部挂掉**（旧版 `sys.exit`） | 逐币 try/except + 失败清单落盘；结构性错误仍硬停 |
| **4** | 0 字节每日文件被 `fetch` **"已存在就跳过"** 掩盖 | `XVSUSDT-1m-2026-09-06.parquet` 是 09-17 被沙箱拦截的写入产物，这次 fetch 直接跳过它 → 合并时才炸 | `--symbols XVSUSDT --force` 定点重下；**教训：下一步的"跳过已有"护栏要能识别 0 字节** |
| **5** | `_build_one` 重算后为空时**旧分片残留** | 若某币因流动性更新被剔出币池，旧分片还在（沙箱删不掉）→ 拼接多写几行 → **meta 与 vectors 行数不一致**（不报错，距离全错） | 重算为空时把分片**覆盖成空数组**（不是删）；本轮未触发，属预防性修复 |
| **6** | 我加的 `import os` **第一次没落盘** | `NameError` → 131 个币全部合并失败 | 改完**立即回读**（这次照做了，第二次确认三处全在）。这是本项目第二次踩"编辑成功≠改上了" |

> ⭐ **本轮最有价值的一处设计**：merge 采用"先写 `.tmp` 再改名"的原子替换，
> 且**下次运行能直接沿用遗留的 `.tmp`**（校验通过就用）。
> 坑 6 触发时磁盘上留下 130 个已算好的成品 → 重跑 **31 秒**完成（否则要重算 **7 分 43 秒**）。
> 同类设计在坑 1 上是反面教材：**缓存必须带自校验**，否则它会在你最想不到的时候静静说谎。

## 6. 这意味着什么 / 局限

- ✅ **库现在追上了行情**：「查历史」的右边界从 08-31 推到 09-21，与「⚡ 看此刻」不再有断档。
- ⚠️ **这不是让检索更准**。方向不可测、波动主要由波幅解释、调仓位换不成钱 —— 这些结论**一个字没变**。
- ⚠️ **增量只带来 +0.7% 的窗口**（8,064 / 1,157,502）。原因不是补得少，而是**币池过滤**：
  每个时点只保留成交额前 20 名，21 天里轮换到的也就 20~23 个币。这是设计如此，不是缺陷。
- ⚠️ **这个窟窿会再长出来**：库是静态的，行情是活的。隔一段时间就得再跑一次。
- ⚠️ **两个币的数据确实止于 09-03**（ICXUSDT / STORJUSDT 在 09-04 下架）。这是**事实**，不是缺漏。
- ⚠️ 步骤 ②「已存在就跳过」的判断**只看文件在不在、不看内容是否完整**（坑 4）。下次跑之前可先扫零字节文件。
